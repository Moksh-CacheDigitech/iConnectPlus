## 1. Purpose

Document the **cryptographic bill of materials (CBOM)** and **key management** practices for iConnect Plus on **Cache Digitech on-premises** infrastructure. **AWS KMS is not the primary key store** in this model; secrets live on-premises (`.env`, restricted files, optional HSM if deployed).

## 2. Cryptographic inventory

| ID | Use case | Algorithm / mechanism | Where applied | Key material location |
|----|----------|----------------------|---------------|------------------------|
| CRYPTO-01 | TLS to users | TLS 1.2+ (nginx) | Edge `erp-nginx` :8443 | `docker/nginx/certs/erp.crt` / `erp.key` |
| CRYPTO-02 | Password storage | bcrypt | API — `sec_user.password_hash` | Per-password salt (in hash) |
| CRYPTO-03 | Session / API auth | HS256 JWT | HttpOnly cookies | `JWT_SECRET_KEY` in host `.env` |
| CRYPTO-04 | Field-level PII/finance | Fernet (AES-128-CBC + HMAC) | Selected ORM columns | `FIELD_ENCRYPTION_KEYS`, `PII_ENCRYPTION_KEY` |
| CRYPTO-05 | MFA | TOTP (RFC 6238) | Optional user MFA | Server-side secret per user |
| CRYPTO-06 | Refresh tokens | Hashed at rest | `sec_refresh_token` | Pepper/hash — not reversible |
| CRYPTO-07 | MinIO | SSE optional / TLS internal | Object API | MinIO root keys in `.env` |
| CRYPTO-08 | PostgreSQL | TLS optional client↔DB | Docker network | **Template / Pending sign-off** |
| CRYPTO-09 | Redis | Optional AUTH | `erp-redis` | **Template / Pending sign-off** |

## 3. In-transit protection

```text
User (LAN/VPN) ──TLS──► nginx ──► web / API containers
                              └──► MinIO (internal HTTP/TLS per config)
```

| Zone | Requirement |
|------|-------------|
| Remote users | VPN mandatory before TLS to application |
| Internal LAN | TLS on reverse proxy; no requirement to expose API on public internet |
| Container east-west | Docker bridge; restrict host firewall to admin paths |

**Explicit non-primary:** AWS KMS, cloud secret managers as **primary** runtime key store — **not used** in this deployment model.

## 6. Key generation & storage rules

1. No cryptographic keys in Git repositories or Docker image layers.  
2. Production `.env` only on application host(s); access limited to break-glass accounts.  
3. Fernet key rotation requires planned maintenance — invalidates unreadable ciphertext if keys dropped without re-encrypt.  
4. JWT secret rotation invalidates active sessions — communicate maintenance window.  
5. Development may use local `.env.example` placeholders — never production values.
